\section{CODESYS codificación manual}
Los Niveles 0 y 1 se han diseñado en Stateflow y el Nivel 2 en Simulink como diagrama de bloques discretos, sin embargo, 
para la implementación en hardware real, se debe traducir la lógica desarrollada a un programa en CODESYS utilizando una mezcla de los lenguajes
diagrama de funciones secuenciales (SFC) y texto estructurado (ST). Este proceso implica mapear 
cada bloque funcional a funciones y estructuras de control equivalentes en SFC y ST, asegurando que la lógica de control se mantenga 
intacta durante la transición al entorno de ejecución real. Puede verse a continuación la estructura resultante:
\begin{figure}[H]
    \centering
    \includegraphics[width=0.5\textwidth]{codesys/arbol_codesys.png}
    \caption{CODESYS - Árbol de componentes.}
\end{figure}

Los 2 POUs principales corresponden a los Niveles 0 y 1, mientras que el Nivel 2 se aplica en Simulink como Matlab functions simil ST
en tiempo discreto. Estos 2 POUs se ejecutan de forma cíclica y en paralelo. Sin embargo en CODESYS debido a la utilización de un PLC 
virtual con una sola CPU, estas tareas se ejecutan de forma secuencial pero de manera intercalada. A pesar de la limitación, se ejecuta 
a tal velocidad que, a fines prácticos, el comportamiento es idéntico al de un sistema con múltiples CPUs ejecutando tareas en paralelo (o múltiples PLCs).

Para el modo automático se realizan algunos cambios. En Stateflow, al entrar al modo automático se pasa por una \textit{junction} para decidir si la ejecución comienza desde cero o si se retoma desde el paso interrumpido. En SFC esto no es posible, ya que el diagrama debe iniciar obligatoriamente en un estado, por lo que se utiliza un estado vacío.
Además, al finalizar el movimiento de \textit{homing}, en Stateflow la transición de salida del modo automático conduce directamente al modo reposo. En cambio, en SFC es necesario incluir una transición o un salto luego del estado para que el programa compile correctamente. Por este motivo, se agrega una transición con condición \textit{FALSE}, la cual nunca se cumple.

\subsection{Comunicación OPC Simulink/CODESYS}
Para poder comunicar el PLC virtual de CODESYS con Simulink, se utilizó el protocolo de comunicación industrial \texttt{OPC-UA}. La versión de CODESYS utilizada (CODESYS V3.5 SP21 Patch 2) cuenta con la posibilidad de montar un servidor OPC-UA y de seleccionar qué variables del programa se quieren exponer a través de este protocolo. Por otro lado, Matlab R2025b cuenta con un cliente OPC-UA que permite conectarse a este servidor y leer/escribir las variables expuestas en tiempo real.

Estos ajustes permiten a Simulink conectarse al servidor OPC-UA de CODESYS sin problemas, y leer/escribir las variables expuestas en tiempo real. Sin embargo, lo hace de forma anónima y sin seguridad alguna, lo cual no es recomendable para un entorno real, pero para fines de simulación y pruebas es suficiente.

Debido a la naturaleza de la comunicación OPC, cada lectura o escritura de una variable implica un proceso de comunicación cliente-servidor que introduce un retardo significativo. Este retardo se vuelve especialmente problemático cuando se intenta realizar lecturas/escrituras a alta frecuencia, lo cual es necesario para el control supervisor y más aún para el control regulatorio. OPC es un estandar de tipo TCP/IP, el cuál está diseñado para sistemas SCADA, con retardos de comunicación de $500$ ms o más, y no para sistemas de control en tiempo real. 

Para mitigar un poco este problema, se decidió implementar bloques de comunicación que se ejecuten a diferentes tiempos de muestreo. Esto enlentece la respuesta del modelo, causando delays peligrosos para la seguridad, pero permite que el sistema funcione de forma estable. El control regulatorio se ejecuta a $100$ ms, el control supervisor y de seguridad a $500$ ms. Para no tener errores con el heartbeat del watchdog, su variable corre al tiempo de muestro original de $20$ ms. De esta forma, se reduce la cantidad de lecturas/escrituras por segundo, disminuyendo la carga en la red y permitiendo Simulink pueda correr a $1$s por segundo de simulación.

Luego de algunas pruebas y reajustes, se mejoró significativamente la fluidez de la simulación, manteniendo una comunicación efectiva entre Simulink y CODESYS. Y se ha podido comprobar de forma satisfactoria que el controlador responde de la misma manera que el modelado en Simulink.

\subsection{Comunicación UDP Simulink/CODESYS}
Debido al retardo que se produce en la comunicación, se considera que OPC no es un protocolo adecuado para la comunicación entre la simulación y el controlador. Para probar esta hipótesis, se implementó una comunicación alternativa utilizando el protocolo UDP, que es un protocolo de comunicación sin conexión y de baja latencia. Esto permite a la simulación correr en tiempo real, sin experimentar retrasos significativos en la comunicación. Se implementó para el control supervisor y de seguridad, dejando de lado el control regulatorio, ya que requiere una mayor velocidad de comunicación que incluso con UDP es difícil de mantener.

La implementación UDP es un poco más compleja, requiere el desarrollo de un protocolo de empaquetado y desempaquetado de datos, así como la sincronización entre los sistemas. Se creó por lo tanto dos programas adicionales en CODESYS, uno para enviar los datos a Simulink (\texttt{COM\_UDP\_TX}), y otro para recibir las variables desde Simulink (\texttt{COM\_UDP\_RX}). 
\begin{figure}[H]
    \centering
    \includegraphics[width=0.5\textwidth]{codesys/com_udp_codesys.png}
    \caption{Nuevas funciones de comunicación UDP en CODESYS.}
\end{figure}

Los archivos de trama son de tipo DUT (Data Unit Type), y se definen como estructuras que organizan los datos a enviar. El orden es vital, ya que por UDP solo se envian bytes en un vector, y el receptor debe conocer el orden y tipo de cada dato para poder desempaquetarlo correctamente. 

Los programas \texttt{COM} se encargan de repartir los valores de las variables a enviar o recibir a sus respectivas posiciones en la trama, y luego utilizan librerías con varibales de envío o recepción.
\begin{figure}[H]
    \centering
    \includegraphics[width=0.9\textwidth]{codesys/com_udp_rx.png}
    \caption{Función de Recepción UDP en CODESYS.}
\end{figure}
\begin{figure}[H]
    \centering

    \caption{Función de Transmisión UDP en CODESYS.}
\end{figure}

En Simulink, al igual que con la comunicación con la animación, se implementaron bloques de lectura/escritura de UDP, permitiendo enviar y recibir datos en tiempo real sin los retrasos de OPC.

Para lograr una sincronización adecuada, se debe programar una tarea en CODESYS que ejecute la funcion de lectura de datos más rápido que la de envío, para evitar pérdida de información. En este caso, se programó a $10$ ms, mientras que el bloque de escritura se ejecuta a $20$ ms. Además, el orden de ejecución también es vital, por lo que la prioridad más elevada es para la lectura (luego el control de seguridad, el control supervisor, y por último el envío de datos). En Simulink es necesario activar \textit{pacing} a tiempo real, es decir, 1 segundo.
